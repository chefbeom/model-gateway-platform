01 · Why AICONNECT

GPU를 늘릴수록, AI 서비스를 쓰는 일은 왜 더 복잡해질까?

처음에는 LM Studio 한 대에 직접 요청하면 충분합니다. 그러나 여러 GPU 서버·서로 다른 모델·팀별 API 키·장애 대응이 더해지면, 주소와 모델 이름을 애플리케이션마다 관리하는 방식은 빠르게 한계에 도달합니다.

PROBLEM 01

서버 주소가 애플리케이션에 새어 나간다

클라이언트가 특정 GPU나 LM Studio 주소를 직접 알고 있으면, 서버 교체·모델 변경·장애 전환 때마다 모든 애플리케이션을 수정해야 합니다.

PROBLEM 02

장애 시 “다음 서버”를 고를 주체가 없다

직접 연결 구조에서는 서버가 내려갔을 때 클라이언트가 대체 서버를 알아야 합니다. 서비스 연속성이 개발자 개인의 재시도 코드에 의존하게 됩니다.

PROBLEM 03

사용량과 비용의 출처가 분산된다

누가 어떤 모델을 얼마나 사용했는지, 어떤 요청이 실패했는지, 어느 GPU가 처리했는지를 한 번에 추적하기 어렵습니다.

PROBLEM 04

외부 AI와 로컬 GPU가 서로 다른 운영 체계가 된다

GPU가 모두 바쁠 때 외부 AI를 써야 해도 별도 API 키와 별도 관측 체계를 만들면 운영 정책과 비용 데이터가 분리됩니다.

03 · Design Principles

처음부터 고정하지 않은 세 가지

GPU 이름

RTX 4090·H100·향후 GPU를 enum으로 고정하지 않습니다. Runtime Endpoint와 Deployment 상태가 라우팅의 기준이며 GPU 정보는 선택적 메타데이터입니다.

실제 모델 파일

사용자는 google/gemma... 같은 공급자 모델 ID가 아닌 text-pro 같은 논리 서비스만 호출합니다.

단일 인프라

LM Studio GPU, 외부 OpenAI 호환 Provider를 동일한 Target으로 취급합니다. 단, 외부 AI 자동 전환은 프로젝트별로 명시적으로 켠 경우에만 허용합니다.

04 · Technology Choices

기능을 위해 고른 기술, 기술을 위해 만든 기능은 아니다

Java 17
Spring Boot 3.5

인증·권한·CRUD·관측 데이터를 하나의 모듈러 모놀리스로 안정적으로 운영하기 위해 선택했습니다. Spring MVC는 관리 API에, WebClient는 LM Studio SSE 프록시와 외부 API 호출에 사용합니다.

Vue 3
TypeScript · Vite

관리자와 일반 개발자의 화면을 분리하고, 실시간 상태 변화 뒤 UI가 즉시 갱신되는 단일 페이지 콘솔을 구현하기 위해 선택했습니다.

MariaDB
JPA · Flyway

사용량·비용·감사 로그처럼 정확성이 필요한 운영 원장을 보관합니다. Flyway로 운영 DB 스키마를 버전별로 안전하게 전환합니다.

Redis

HA Compose에서 API Gateway 두 대가 RPM, 동시 요청, 잠금 같은 공유 상태를 일관되게 볼 수 있도록 사용합니다.

LM Studio

이미 준비된 로컬 LLM Runtime을 OpenAI 호환 API로 연결합니다. 플랫폼은 GPU 드라이버를 관리하지 않고, 준비된 Runtime을 제어·감시하는 역할에 집중합니다.

Tailscale · Nginx

GPU Runtime은 인터넷에 직접 공개하지 않고 Tailscale 사설망으로 Gateway만 접근하도록 구성합니다. Nginx는 TLS·SSE·로드 밸런싱의 진입점입니다.

Resilience4j

Endpoint별 Circuit Breaker와 제한된 재시도를 적용합니다. 이미 사용자에게 스트리밍된 응답은 무리하게 이어붙이지 않는 안전한 Failover 정책을 유지합니다.

Actuator · Micrometer
Prometheus · Grafana

MariaDB의 정확한 청구 원장과 시계열 모니터링을 분리합니다. Prometheus는 추세·알림, Grafana는 운영 대시보드를 담당합니다.

07 · Q&A

도입·운영 과정에서 예상되는 질문과 답변

AICONNECT를 실제 조직에 도입하거나 포트폴리오를 설명할 때 자주 나올 질문을 기준으로 정리했습니다. 각 답변은 설계 의도, 동작 방식, 도입 판단 기준, 결론을 함께 담습니다.

왜 Standalone, HA Compose, Kubernetes의 세 가지 배포 구조를 모두 제공하나요?

LLM Gateway의 기능은 같아도 운영 조직의 규모와 역량은 다릅니다. 개인이나 소규모 팀은 빠른 설치와 낮은 운영 비용이 중요하고, 중간 규모 조직은 Gateway 장애를 줄이되 Kubernetes까지 운영하고 싶지 않을 수 있습니다. 대규모 조직은 수평 확장, 자동 복구, 배포 표준화가 필요합니다. 하나의 배포 방식만 제공하면 어떤 사용자에게는 과도하게 복잡하거나 반대로 너무 취약해집니다.

  • Standalone: Gateway 1대, MariaDB, Nginx를 한 VM 또는 호스트에 두는 구성입니다. Docker Compose와 Tailscale만 준비하면 되므로 PoC·개인·소규모 사내 도입에 적합합니다. 단일 Gateway와 단일 호스트가 장애 지점입니다.
  • HA Compose: Load Balancer 뒤에 Gateway 2대를 두고 Redis로 공유 상태를 관리합니다. Kubernetes 없이도 Gateway 한 대의 장애에는 견딜 수 있습니다. 단, 두 Gateway가 같은 호스트에 있으면 호스트 장애까지 해결하지는 못합니다.
  • Kubernetes: Gateway를 Deployment로 관리하고 HPA, PDB, Rolling Update, Ingress/Gateway API로 다수 노드에 분산합니다. 클러스터·네트워크 정책·시크릿·DB/Redis의 고가용성을 함께 운영할 수 있는 조직에 적합합니다.

결론: 코드와 API 계약은 하나로 유지하되 설치 방식만 운영 성숙도에 맞춰 선택하는 것이 핵심입니다. 작은 팀은 Standalone으로 시작하고, 요구가 커지면 HA Compose를 거쳐 Kubernetes로 확장할 수 있습니다.

각 배포 구조의 차이와 전환 시점은 무엇인가요?

전환 기준은 GPU 수보다 Gateway가 멈췄을 때의 업무 영향, 동시 요청량, 운영 자동화 필요성입니다. GPU 노드는 어느 구조에서도 Tailscale 또는 조직 사설망으로 Gateway에 붙을 수 있습니다.

  • Standalone 유지: 중단 시 수동 재시작이 가능하고 단일 Gateway 장애가 업무에 치명적이지 않을 때입니다.
  • HA Compose 전환: 재시작 중에도 API를 제공해야 하거나 여러 Gateway가 같은 Rate Limit·동시 요청 정책을 공유해야 할 때입니다.
  • Kubernetes 전환: 인스턴스를 자주 늘리고 줄여야 하거나 물리 노드 분산, 자동 복구, 무중단 배포가 조직 표준일 때입니다.

HA Compose의 Gateway 2대가 한 VM에 있으면 프로세스 장애는 줄어도 CPU, RAM, 디스크, 네트워크가 동시에 사라지는 호스트 장애는 막지 못합니다. 이는 단일 호스트 고가용성이지 인프라 고가용성은 아닙니다.

결론: 서비스 계약과 사용량 흐름은 Standalone에서 먼저 검증하고, Gateway 중단 비용이 커지면 HA Compose로, 물리 노드 분산과 자동 확장이 필요해지는 순간 Kubernetes로 전환하는 순서가 현실적입니다.

Redis는 왜 필요하며, Standalone에서는 왜 선택 사항인가요?

Gateway가 한 대라면 API Key 캐시, RPM, 현재 처리 중인 요청 수, Circuit Breaker 상태를 JVM 메모리에 둬도 모순이 없습니다. 요청이 모두 같은 프로세스를 통과하기 때문입니다. 이때 Redis를 추가하면 설치와 장애 지점만 늘어날 수 있습니다.

Gateway가 두 대 이상이면 각 인스턴스의 메모리는 서로 보이지 않습니다. 예를 들어 분당 60회 제한이 있어도 Gateway A와 B가 각각 60회를 허용하면 실제로는 120회가 허용됩니다. 같은 Deployment의 동시 요청 제한과 분산 잠금도 같은 문제가 생깁니다.

  • HA에서 Redis는 공유 Rate Limit, 동시 요청 카운터, 분산 락, 공유 캐시를 담당합니다.
  • MariaDB는 사용량·비용·요청 이력의 정확한 원장이고, Redis는 빠르게 변하는 운영 상태입니다.
  • Redis 장애 시에는 보수적으로 차단할지, 제한 기능만 축소할지 정책을 명시해야 합니다. 무조건 fail-open 하면 Quota가 우회될 수 있습니다.

결론: Redis는 “더 빠른 DB”가 아니라 여러 Gateway가 하나처럼 동작하게 만드는 공유 상태 계층입니다. Gateway가 하나일 때는 선택 사항이고, 두 대 이상부터는 사실상 필수입니다.

왜 사용자는 실제 GPU 주소나 LM Studio 모델명을 직접 호출하지 않나요?

사용자가 GPU 서버 주소를 직접 호출하면 API Key 권한, 사용량 집계, Rate Limit, 장애 전환, 감사 로그를 중앙에서 강제할 수 없습니다. GPU 교체나 모델 파일 변경 때마다 모든 애플리케이션 설정도 바꿔야 합니다.

AICONNECT는 논리 서비스(Logical Service)를 공개합니다. 사용자는 text-pro만 호출하고, 관리자는 내부에서 Gemma·Qwen·외부 Provider의 특정 Deployment에 연결합니다. Target 우선순위만 바꾸면 API Key, Base URL, 사용자 코드의 model 값은 변하지 않습니다.

결론: 논리 서비스는 사용자와 인프라 사이의 계약입니다. GPU와 실제 모델은 교체 가능한 구현이고, text-pro는 지속되어야 하는 공개 인터페이스입니다.

Failover는 언제 자동으로 일어나고, 스트리밍 응답도 이어서 받을 수 있나요?

Failover는 Target Health, Circuit Breaker, 동시 요청 여유, 필수 Capability, 우선순위를 기준으로 후보를 고르는 과정입니다. Primary 연결이 거부되거나 응답 헤더·첫 토큰 전에 실패하면 Gateway는 다음 Target으로 안전하게 재시도할 수 있습니다.

이미 일부 토큰을 사용자에게 보낸 스트림은 다른 모델의 답변을 뒤에 붙일 수 없습니다. 앞부분 중복, 문맥 불일치, JSON 손상, 이중 과금 가능성이 생기기 때문입니다. 이 경우 현재 스트림은 오류로 끝내고, 다음 요청부터 대체 Target을 사용합니다. SAFE는 도달 전 연결 실패만, AGGRESSIVE는 일부 5xx·첫 토큰 지연까지 재시도하지만 중복 추론 위험이 있습니다.

결론: API Key를 바꾸지 않고 다음 요청이 정상 처리되는 것이 현실적인 무중단의 정의입니다. 이미 전송된 스트림을 억지로 이어 붙이지 않는 것이 더 안전합니다.

외부 OpenAI API를 등록하면 사용자가 그 API Key를 직접 쓰게 되나요?

아닙니다. 외부 Provider Key는 관리자가 조직 단위로 암호화해 등록하는 내부 자격 증명입니다. 사용자는 여전히 AICONNECT 프로젝트 API Key와 AICONNECT Base URL만 사용합니다.

관리자는 Provider Base URL, 모델 ID, 가격, 사용 가능 여부를 등록하고 이를 Deployment/Target으로 논리 서비스에 연결합니다. 모든 요청은 Gateway를 통과하므로 외부 AI를 썼더라도 프로젝트·API Key·논리 서비스·실제 Provider별 입력/출력 토큰, 비용, 오류를 같은 원장에서 관찰합니다. 자동 Failover는 프로젝트 정책에서 명시적으로 켠 경우에만 허용하는 것이 비용 통제에 적합합니다.

결론: 외부 AI는 별도의 우회 경로가 아니라 또 하나의 추론 Target입니다. 사용자에게 외부 키를 노출하지 않으면서도 로컬 GPU와 같은 권한·비용·관측 체계 안에서 운영합니다.

MariaDB에 프롬프트와 응답까지 모두 저장하나요? 개인정보는 어떻게 다루나요?

Gateway를 통과한다는 사실과 원문을 영구 보관한다는 사실은 다릅니다. 기본 정책은 METADATA_ONLY입니다. 요청 ID, 사용자/프로젝트/API Key, 논리 서비스, 실제 Deployment, 토큰, 비용, 지연 시간, 오류, Failover만 저장하고 원문 프롬프트와 응답은 저장하지 않습니다.

감사나 디버깅이 꼭 필요한 프로젝트에는 마스킹 저장 또는 FULL_ENCRYPTED를 선택할 수 있습니다. API Key와 LM Studio Token은 로그나 관측 라벨에 절대 기록하지 않고, 원문 열람은 제한된 관리자에게만 허용하며 감사 로그를 남겨야 합니다. Prometheus에는 요청 ID·사용자 ID·프롬프트를 label로 넣지 않아야 합니다.

결론: 운영에 필요한 최소 메타데이터와 민감 원문을 분리합니다. 기본값은 원문 미저장이며, 보관이 필요할 때만 명시적 정책·암호화·감사를 추가합니다.

왜 Prometheus와 Grafana만으로 사용량·비용을 관리하지 않나요?

Prometheus는 CPU, 오류율, p95 지연 시간, 활성 연결처럼 시간에 따라 변하는 시스템 메트릭을 빠르게 분석하는 도구입니다. API Key별 정확한 청구, 과거 가격 스냅샷, 요청 Attempt, 삭제/감사 관계는 MariaDB 같은 관계형 원장에서 관리해야 합니다.

AICONNECT는 MariaDB를 사용량과 비용의 source of truth로 둡니다. Prometheus에는 llm_gateway_requests_total, 지연 시간, 활성 요청, Failover 횟수, 노드 Health, Circuit Breaker 상태를 보냅니다. Grafana는 이를 시각화하고 알림을 실행합니다.

결론: MariaDB는 “누가 무엇을 얼마나 사용했는가”를 정확히 답하고, Prometheus/Grafana는 “시스템이 지금 건강한가”를 빠르게 답합니다. 둘은 역할이 다른 보완재입니다.

Tailscale은 왜 사용하고, GPU 서버를 인터넷에 공개하지 않는 이유는 무엇인가요?

LM Studio Runtime은 공개 API Gateway가 아니라 내부 추론 실행기입니다. 인터넷에 직접 공개하면 공격 표면이 넓어지고, 사용자 API Key와 Runtime 내부 Token의 역할이 섞이며, 방화벽·TLS·접근 제어를 모든 GPU 서버에서 별도로 관리해야 합니다.

AICONNECT는 외부 사용자에게 Gateway만 공개하거나 private-only 배포에서는 Tailnet/VCN 내부에만 Gateway를 노출합니다. Gateway와 GPU Runtime 사이에는 Tailscale 사설망을 사용하고, ACL로 Gateway가 GPU 노드의 LM Studio 포트에만 접근하게 제한합니다. GPU 노드는 공인 포트를 열 필요가 없습니다.

결론: Tailscale은 모델 추론 트래픽을 관리된 사설망 안으로 넣는 수단입니다. 사용자는 GPU 주소를 모르고, 운영자는 Gateway 한 곳에서 정책과 감사를 적용합니다.

조직·팀·프로젝트·개발자 권한은 왜 여러 단계로 나누나요?

모든 사용자가 같은 권한을 가지면 운영자는 인프라를 안전하게 관리하기 어렵고 개발자는 필요한 API Key조차 발급받기 불편합니다. AICONNECT는 책임 범위에 따라 권한을 분리합니다.

  • 최종 관리자: 조직 전체 Runtime, 외부 AI, 서비스 정책, 사용자/팀, 모든 사용량과 감사 로그를 관리합니다.
  • 팀 또는 프로젝트 소유자: 자신이 소유한 프로젝트, 서비스 접근 권한, 프로젝트 전체 API Key와 사용량을 관리합니다.
  • 일반 개발자: 참여 프로젝트에서 자신이 발급한 API Key와 사용량을 확인하고 호출합니다. 인프라와 라우팅은 수정할 수 없습니다.

프로젝트와 서비스 삭제도 연결된 API Key, 권한, 요청 이력을 검사합니다. 감사 보존이 필요하면 삭제를 막고 중지·폐기 절차를 안내합니다.

결론: 권한 계층은 UI를 복잡하게 하려는 장치가 아니라 인프라 제어 권한과 API 소비 권한을 분리해 책임과 감사 범위를 명확히 하는 보안 모델입니다.

LM Studio 모델 로드 설정을 플랫폼에서 어디까지 제어하는 것이 적절한가요?

플랫폼은 모델 다운로드, 로드/언로드, 컨텍스트 길이, GPU Offload, CPU Thread Pool, Unified KV Cache, 메모리 유지, Flash Attention, K/V Cache 양자화처럼 운영자가 반복적으로 조절하는 핵심 설정을 지원할 수 있습니다. 나머지 고급 옵션은 LM Studio 기본값을 우선 사용하는 편이 안전합니다.

GPU마다 VRAM, 드라이버, 모델 양자화, 컨텍스트 길이, 다른 프로세스 점유 상태가 달라 “H100이니까 무조건 이 값” 같은 규칙이 성립하지 않기 때문입니다. 플랫폼은 GPU 드라이버를 고치거나 직접 스케줄링하는 도구가 아니라 이미 준비된 Runtime의 상태와 모델 운영을 제어하는 계층입니다.

결론: 자주 바꾸고 서비스 품질에 직접 영향을 주는 설정만 노출하고, 나머지는 LM Studio 기본값으로 두는 것이 안전성과 사용성의 균형점입니다.

06 · Engineering Lessons

개발하면서 실제로 마주한 문제와 설계 수정

01 / SCOPE

GPU별로 나누던 사고를 Endpoint·Deployment 모델로 바꿨다

처음에는 보유 GPU를 중심으로 설계하기 쉬웠습니다. 하지만 조직마다 장비가 달라지고 새 GPU는 계속 등장합니다. 그래서 등록 단위를 GPU가 아닌 Inference Node → Runtime Endpoint → Model Deployment로 분리했습니다.

02 / SECURITY

사용자 API Key와 LM Studio Token을 분리했다

프로젝트 API Key는 Gateway가 검증하고, GPU Runtime에는 Gateway만 아는 내부 토큰을 사용합니다. GPU 서버 주소·자격 증명을 사용자에게 직접 주지 않아도 됩니다.

03 / FAILOVER

스트리밍 중간에는 “무중단 재개”를 약속하지 않았다

일부 토큰을 이미 전달한 스트림을 다른 모델에서 이어 붙이면 중복·문맥 불일치·깨진 JSON이 발생할 수 있습니다. 첫 토큰 전 실패는 자동 전환하고, 중간 실패는 현재 요청을 오류로 종료한 뒤 다음 요청부터 대체 Target을 사용하도록 경계를 명확히 했습니다.

04 / OBSERVE

정확한 사용량 원장과 모니터링을 분리했다

Prometheus는 고유 요청 ID나 정확한 과금 원장에 적합하지 않습니다. 따라서 토큰·비용·요청 Attempt는 MariaDB에 기록하고, Prometheus/Grafana는 지연 시간·오류율·활성 요청·노드 상태를 관찰합니다.

05 / HA

다중 Gateway에서는 상태 공유와 배포 이름의 중요성을 확인했다

두 Gateway를 운영할 때 Redis가 없으면 Rate Limit·동시 요청 상태가 분리됩니다. 또한 Compose 재배포에서는 프로젝트명을 고정해 기존 HA 스택과 다른 임시 스택이 생기지 않도록 운영 절차를 정리했습니다.

06 / UX

관리자의 복잡함을 개발자 화면에 그대로 노출하지 않았다

관리자는 Runtime·모델·Target·팀·감사를 다뤄야 하지만 개발자는 프로젝트, API 키, 허용 모델, 사용량만 필요합니다. 역할별 화면과 즉시 반영 UI, 입력 도움말을 통해 운영 복잡도를 사용자 경험에서 분리했습니다.

08 · Expected Impact

AI 인프라를 바꾸어도, 사용하는 서비스는 멈추지 않게

StableGPU·모델 파일·양자화 변경과 사용자 API 계약을 분리
Visible요청부터 실제 배포, 토큰, 비용, 오류까지 하나의 추적 경로
Governed조직·팀·프로젝트·API 키 역할에 맞춘 접근 제어와 감사
ScalableStandalone, HA Compose, Kubernetes로 같은 코드베이스를 확장

Operation Scenario

회사 내부 AI API 사용 흐름

  1. 관리자가 Tailscale로 연결된 LM Studio Runtime을 조직에 등록합니다.
  2. 발견한 모델 Deployment를 text-pro 논리 서비스의 Target으로 연결합니다.
  3. 프로젝트 소유자가 팀 프로젝트를 만들고 필요한 서비스 권한을 부여합니다.
  4. 개발자는 프로젝트 API Key를 발급받아 OpenAI SDK의 Base URL만 바꿉니다.
  5. 운영자는 사용량·장애·실제 처리 Target을 확인하고 필요 시 정책을 변경합니다.
