# 프로젝트 권한 및 외부 GPU 보안 구현 기준

이 문서는 목표 설계이며 구현 완료나 운영 적용을 의미하지 않는다.

## 권한과 초대

- 최종 관리자는 배포 시 생성하고 일반 초대로 생성하지 않는다. 모든 사용자는 HTTPS와 MFA로 접속한다.
- 프로젝트 관리자 권한은 조직 전체가 아니라 명시적으로 지정된 프로젝트에만 적용한다. 팀 공유 여부와 무관하게 프로젝트별로 확인한다.
- 프로젝트 관리자는 자신이 관리하는 프로젝트의 일반 사용자만 초대하고 API 키 발급 권한을 위임한다. 상위 권한 또는 다른 프로젝트 권한을 부여할 수 없다.
- 초대는 이메일에 묶인 만료형 일회용으로 발급하며, 수락 시 현재 초대 권한과 프로젝트 상태를 다시 확인한다.
- 기존 PROJECT_DIRECTOR 초대는 ORGANIZATION_ADMIN을 부여하므로 이 동작을 변경하고 기존 계정의 권한 이행을 별도로 검토해야 한다.

## 연결 승인 및 데이터 경계

- Runtime 및 Provider 등록 신청과 실제 연결을 분리한다. 대기 중인 주소로 자동 probe, 모델 조회 또는 추론을 하지 않는다.
- 최종 관리자는 신청 내용과 연결 대상을 검토한 뒤 승인한다. 등록 승인과 프로젝트의 사용 승인은 별도로 기록한다.
- 대상은 사내, 승인된 외부 비보존 GPU, 일반 외부로 구분한다. 외부 비보존은 외부 전송이 없는 것이 아니라 계약과 설정을 검토한 예외다.
- 외부 비보존 승인에는 근거, 승인자, 범위, 만료일 및 철회 상태를 기록한다. 주소·업체·처리 위치·보존 정책 변경 시 재승인을 요구한다.
- 프로젝트, 논리 서비스, API 키 정책은 교집합으로 적용한다. 하위 정책은 상위를 완화하지 못한다. 미분류·만료·철회 대상은 외부 비보존으로 취급하지 않는다.
- 외부 GPU 사용 허용과 장애 시 자동 전환은 별개이며 자동 전환 기본값은 꺼짐이다. 허용 대상이 없으면 명확한 오류를 반환한다.
- 위 제한은 일반·스트리밍·재시도·대기열·테스트 콘솔 및 직접 호출 경로에 공통 적용한다. 승인 철회나 만료는 신규 요청에서 즉시 반영한다.

## 한도 및 HA

- 최종 관리자 상한 아래에서만 프로젝트 관리자가 프로젝트와 키 한도를 지정한다. 동시 요청은 원자적으로 한도를 예약하며 실패·취소 시 정리한다.
- 초대 사용, 승인·철회, 한도 예약은 두 API 인스턴스에서 원자적으로 처리한다. 인스턴스 장애 후 예약 복구와 스트리밍 취소를 검증한다.
- 감사 로그에는 승인·정책·권한 변경과 판단 근거를 기록하되 API 키와 요청 원문은 기록하지 않는다.

## 도입 및 검증

1. 기존 운영 계정, 조직·팀·프로젝트 매핑, 활성 API 키 및 라우팅을 확인한다. 기존 동작을 무단으로 변경하지 않는다.
2. 명시적 프로젝트 권한과 연결 승인 저장 구조를 추가하고 기존 데이터에 대한 이행·롤백 절차를 작성한다. 모호한 외부 대상은 보수적으로 분류한다.
3. 서버 측 접근 제어와 라우팅 판단을 공통화하고 API 및 콘솔을 연결한다. UI 숨김만으로 접근을 차단하지 않는다.
4. 교차 프로젝트 접근, 권한 상승, 만료·철회, 위변조, 병렬 승인, 모든 요청 경로의 우회 및 HA 장애를 자동 테스트한다.
5. 비운영 환경에서 마이그레이션·복구·실제 연결을 검증한 후 운영 공개와 배포를 별도로 진행한다.
