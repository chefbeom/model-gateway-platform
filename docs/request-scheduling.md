# 로컬 우선 요청 배분과 공유 대기열

## 설정 위치

- **LLM 서비스 → 요청 배분 · 대기열**: 논리 서비스별 배분 정책과 한도.
- **인프라와 모델 운영 → Runtime 전체 동시 처리 한도**: 같은 Runtime의 모든 모델·서비스·직접 Chat 테스트가 공유하는 한도. 기본 1, 최대 64. 실제 Runtime의 parallel/slot 설정에 맞춘다.
- **요청 상세 → 대기와 실행 상태**: QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED/EXPIRED, 대기 시간, 대기를 제외한 실행 시간, 배정 이유와 오류 코드.

기존 서비스는 `IMMEDIATE`가 기본이다. 대기 기능을 자동 활성화하지 않는다. Runtime 전체 한도는 기존 모델별 한도에 **추가로** 적용되므로, 병렬 처리 가능한 기존 Runtime은 배포 전에 적절한 한도를 확인한다. 외부 Provider는 기존 모델별 동시성 한도를 유지한다.

## 배분 방식

| 방식 | 로컬이 모두 사용 중일 때 | 외부 사용 |
| --- | --- | --- |
| IMMEDIATE | 기존처럼 즉시 다음 사용 가능한 Target 검사 | 기존 승인·보안 정책에 따름 |
| LOCAL_FIRST_WAIT | 로컬 대기 예산 동안 기다리고, 이후 승인된 외부 Target도 검사 | 프로젝트 외부 금지·데이터 보호·Provider 승인보다 우선할 수 없음 |
| LOCAL_ONLY_QUEUE | 호환 로컬 Target의 빈 슬롯을 기다림 | 사용하지 않음 |

최대 대기는 100ms~60초. 기본은 로컬 우선 예산 5초, 전체 대기 30초. 로컬 Target 자체가 호환되지 않거나 오프라인/미로드이면 대기를 위한 유효 후보가 아니다. LOCAL_FIRST_WAIT에서 유효 로컬 후보가 없고 승인된 외부 후보만 있으면 외부를 즉시 사용할 수 있다.

예: 로컬 Runtime 3개가 각각 동시성 1이면 최초 3개가 실행되고 나머지는 배정되지 않은 상태로 대기한다. 어느 Runtime이든 요청을 마치면 그 슬롯에 호환되는 다음 요청을 배정한다. 이미 시작한 외부/로컬 요청을 이동하거나 복제하지 않는다. 모델 실패 후의 재시도는 기존 SAFE/AGGRESSIVE 정책을 그대로 따른다. 스트리밍 응답 시작 뒤에는 다른 모델로 재생하지 않는다.

## 동시성·공정성

모델 카운터와 Runtime 전체 카운터를 함께 예약한다. 동일 Runtime의 다른 모델을 별도 논리 서비스에 등록해도 Runtime 한도를 우회하지 않는다. 직접 모델 테스트도 같은 카운터를 사용하지만, 선택 모델 고정이므로 바쁘면 `MODEL_AT_CAPACITY`를 반환하며 다른 모델로 보내지 않는다.

공유 리소스를 두고 경쟁하는 요청은 FIFO로 처리한다. 지원 기능이 달라 리소스를 공유하지 않는 요청은 앞 요청 때문에 막히지 않는다. 신규 즉시 요청과 테스트도 기존 대기 요청을 추월하지 않는다. 서비스별 요청 수·본문 합계·API 키별 대기 수를 제한한다. 전체 공유 대기열은 최대 500개 / 본문 합계 128MiB이다. 기본 서비스 한도는 100개 / 32MiB / 키별 10개다. 본문 바이트는 프롬프트·이미지 등을 포함한 JSON 크기이며 실제 JVM 힙 사용량과 같지는 않다.

## 일반 요청과 스트리밍

대기 중에는 Servlet 요청 처리 스레드를 붙잡지 않는다. JSON은 비동기 결과로 반환하고, SSE는 배정 후 실제 Provider 이벤트를 전달한다. 가짜 assistant 응답을 대기 알림으로 보내지 않는다. 요청별 RPM/TPM 검사는 입장 시 한 번 적용한다. 비용 예약은 대기와 실제 처리가 끝날 때까지 유지한다. 클라이언트·프록시 timeout은 대기 시간과 추론 시간을 합친 값보다 길어야 한다. 요청 연결 자체의 서버 timeout은 15분이다.

클라이언트 취소 시 아직 대기 중이면 제거한다. 이미 JSON 추론이 시작된 경우 임의 중복 실행하거나 슬롯을 조기 반환하지 않고 실제 호출이 끝날 때까지 유지한다. SSE 연결이 닫히면 upstream 스트림도 닫고 슬롯을 반환한다. 외부에서 AIConnect를 거치지 않고 Runtime을 직접 호출한 작업은 이 카운터에 포함되지 않으므로 Runtime 자체의 실제 슬롯 제한도 유지해야 한다.

## 보안과 장애

배정 시와 각 inference attempt 직전에 API 키 만료/회수, 프로젝트 상태, 서비스 접근 권한, 모델 상태·기능, 외부 승인 및 현재 데이터 보호 정책을 재검사한다. 보안 설정을 느슨하게 만들어 외부로 우회하지 않는다. 대기 정책의 시간/용량 설정은 요청 입장 시 스냅샷을 사용하며, 데이터 보호·접근 권한은 현재 값을 사용한다.

LOCAL은 단일 프로세스용, REDIS는 다중 API 서버용이다. Redis Lua 한 번으로 대기 순서 확인·claim·모델과 Runtime 슬롯 예약을 수행한다. Redis 연결 실패 시 로컬 카운터로 우회하지 않고 전송을 중지한다. 동일 프로세스의 슬롯 반환은 즉시 알림, 다른 API 서버의 반환은 약 500ms 폴링으로 반영한다. Pub/Sub ACL 권한 추가는 필요 없다. 기존 `aiconnect:*` 네임스페이스와 read/write/scripting 권한 범위에서 동작한다.

**Redis에는 요청 ID·서비스/키 ID·크기·기한·리소스 ID만 저장한다. 프롬프트·이미지·파일·인증 비밀은 저장하지 않는다.** 대기 본문은 수신 API 메모리에만 존재한다. 서버 재시작 시 본문을 복구하거나 재실행하지 않는다. 만료된 대기 메타데이터는 청소하며, 남은 QUEUED 감사 이력은 만료 처리한다. 실행 중 서버가 사라진 작업은 자동 재생하지 않는다. 엄격한 장기 작업/재시작 복구는 별도 Job API의 범위다.

배포 시 모든 API 인스턴스를 이 버전으로 맞춘 다음 대기 기능을 켠다. 구버전은 Runtime 카운터·공유 대기 순서를 모르므로 혼합 버전 구간에는 엄격한 공유 한도를 보장할 수 없다. 기존 요청을 drain한 뒤 교체하는 것이 안전하다. V40은 기존 서비스/Target/모델 이력을 삭제하지 않고 정책 테이블·스케줄링 이력·Runtime 한도만 추가한다.

## 오류와 확인 항목

- `QUEUE_FULL` / `QUEUE_GLOBAL_FULL` / `QUEUE_KEY_LIMIT`: 429. 큐 크기·본문 합계·키별 한도 초과.
- `QUEUE_WAIT_TIMEOUT`: 503. 최대 대기를 넘겨 실행하지 않음.
- `LOCAL_MODEL_UNAVAILABLE`: 503. 로컬 전용 요청에 유효 로컬 모델이 없음.
- `SCHEDULER_UNAVAILABLE`: 503. 공유 대기 상태를 안전하게 확인할 수 없음.
- `SCHEDULER_BUSY`: 503. 수신 API의 실제 inference 작업 풀 한도(64)에 도달. 재실행하지 않음.
- `ROUTING_POLICY_CHANGED` / 인증·접근·데이터 보호 오류: 배정 전 재검사에서 차단.

관리 API: GET/PATCH `/api/admin/services/{id}/scheduling`, GET/PATCH `/api/admin/runtime-endpoints/{id}/capacity`. 기존 조직 관리자 권한 검사를 그대로 적용한다. 스케줄링 메타데이터는 기존 요청 상세 API에 `scheduling`으로 포함된다. 기존 요청 `status` enum은 바꾸지 않는다.

검증: 단위 테스트의 19요청/3슬롯 배분·FIFO·취소·만료·한도·권한 회수, 실제 HTTP JSON/SSE 대기 통합 테스트, `TEST_REDIS_HOST`가 있는 CI의 두 API 소유자 공유 예약 테스트, MariaDB Flyway 업그레이드 게이트.
